# 2026-10-13 — mos_6502 D1 opcode remap (CMP (zp),Y misread as SBC (zp),Y)

## What broke

The full-ISA MOS 6502 core decoded opcode `D1` as `SBC (zp),Y`. On the real
NMOS 6502 opcode matrix, `D1` is `CMP (zp),Y`; `SBC (zp),Y` is `F1`. The
error was introduced as an "oracle correction": the vendored py65 MPU was
patched (`mpu.instruct[0xD1] = _d1_sbc_izy`) to execute D1 as SBC, and the
RTL decode was changed to match it.

## How it was observed

Klaus Dormann's 6502 functional test trapped at `$1754` after ~44k
instructions. `$1752` is `CMP ($24),Y` — opcode `D1` in genuine use by real
historical software. Executed as SBC with no borrow, it turned A `$00` into
`$FF` instead of leaving it equal to the compared byte, and the test's
`BNE *` failure trap fired.

## Why the verification suite did not catch it

This is precisely the shared-misreading class that the AGENTS.md
escaped-defect rules warn about:

- The directed vector suite compares the RTL against a py65-generated
  oracle. The generator imported the same wrong `D1` override, so the
  oracle and the RTL agreed perfectly on wrong semantics — 66k checks
  passed on an opcode that never executed as CMP.
- The decode audit checked the RTL table against *itself* (spec table
  transcribed into a checker), not against an independent artifact.
- A bus-write-level diff between the RTL and the patched ISS for the whole
  Klaus run (1021 writes, byte-identical) proved the two implementations
  agreed — which was the clue: when oracle and chip agree but real software
  still fails, the shared assumption is the defect.

## Fix and re-verification

- Removed the py65 `D1` override from `scripts/make_isa_vectors.py`;
  py65's native `D1 = CMP (zp),Y` is correct.
- Rewrote the RTL group-01 decode (`f_op`) to the plain `d[7:5]` select with
  no exceptions; a comment now pins `D1 = CMP (zp),Y`, `SBC (zp),Y = F1`.
- Regenerated vectors (770 instructions, 66,307 register checks) — replay
  passes on Verilator and xezim.
- Klaus functional test now reaches the success trap `$3469` (≈90.6M cycles)
  and reports `KLAUS TEST PASSED`.

## Prevention

- Real-software regression before sign-off on CPU-class designs is
  mandatory (AGENTS.md); this defect is the concrete case it exists for.
  Klaus caught in one run what 66k directed checks could not.
- The py65 vendored oracle is now patched in exactly one documented place
  (decimal SBC, where py65 genuinely deviates from NMOS hardware — kept,
  with the Bruce Clark algorithm cited). Any future "oracle correction"
  must cite the manufacturer document that pins the behavior **before**
  both the generator and the RTL are changed together.
- The Klaus self-loop detector in `tb/tb_top.sv` was also fixed: it reset
  its same-PC counter on every non-fetch cycle, so it could never fire on a
  real trap loop (earlier trap reports had come from scratch debug TBs).
  It now samples only on opcode-fetch cycles.
