# Session History: Intel 4004 Implementation and Verification

## Goal

Build the Intel 4004 — the first commercially available microprocessor
(MCS-4 CPU, announced November 15, 1971) — as a complete historical chip
design under `design/intel_4004/`, including a sourced specification and
README, implementation and verification plans, synthesizable SystemVerilog
RTL, deterministic simulation against an independent instruction-set
simulator, formal proof of the full ISA transition function, generic
synthesis, fail-fast scripts, reports, and design-index integration.

## Architecture and scope

- Implemented a single-clock functional reconstruction of the 4004 as one
  module, `design/intel_4004/src/intel_4004.sv`: the 8-period instruction
  cycle (A1 A2 A3 M1 M2 X1 X2 X3) as an internal phase sequencer, the
  multiplexed 4-bit bus (`data_i`/`data_o`/`data_oe`), `sync`, `cm_rom`, and
  four bank-decoded `cm_ram` command lines.
- Implemented all 45 instructions of the MCS-4 manual's repertoire plus WPM
  (program-memory half-byte write for 4008/4009 systems): 16 basic, 15
  I/O/RAM, 14 accumulator-group — the commonly cited 46 total.
- 12-bit program counter held in a four-register circular push-down stack
  (3-level nesting, documented deepest-entry-loss overflow); 16 index
  registers; SRC pointer; DCL command-line register.
- The historical program-counter increment happens once per instruction
  cycle; the core holds the PC frozen at the fetched word and applies the
  advanced value (PC+1/PC+2) at a single architectural commit edge (end of
  the instruction's final X3), which reproduces the documented JCN/JIN/FIN/
  ISZ page-straddle quirks by construction.
- Undefined opcode combinations (1111 1110, 1111 1111) execute as NOPs.
- Added a synchronous active-low `rst_n` clearing all registers (the manual
  documents that a sustained RESET clears everything, including the dynamic
  index-register array); documented the asynchronous-reset and two-phase
  clock exclusions in spec section 11.

## Research findings that shaped the implementation

- The scanned MCS-4 manual (codeabbey mirror of the original PDF) confirms:
  45 instructions in the CPU repertoire with WPM documented for 4008/4009
  systems (46 total), a 4x12 address stack (3 return levels, circular
  overwrite on the fourth JMS), JCN targets within the same 256-word ROM,
  DCL/SRC command-line operation, and reset clearing all registers.
- SUB/SBM add the INVERTED carry (`ACC + ~operand + ~CY`, CY=1 = no borrow),
  per the manual's SBM equation and hardware-validated implementations
  (MAME MCS-40 core, which executes the original Busicom ROMs). An initial
  RTL draft using `+CY` for SUB/SBM was off by one when CY=0 and was fixed;
  the spec documents the convention and the manual's SUB-line inconsistency.
- JCN condition bit order (bit3=invert, bit2=ACC-zero, bit1=carry,
  bit0=TEST-low) confirmed against MAME after the scanned manual's OCR
  proved ambiguous.
- Undefined opcodes behave as NOPs per the real decoder.

## Implementation and verification

- Deterministic self-checking simulation (`tb/tb_intel_4004.sv`, xezim):
  a behavioral MCS-4 microsystem (4001 ROM with I/O ports and WPM shadow,
  4002 RAM with main/status/output memories) responds on the multiplexed
  bus while an independent instruction-set simulator with shadow memories
  steps in lockstep. 165,778 cycles, 20,192 instruction boundaries compared
  with zero mismatches; directed program executes all 46 instructions
  (testbench fails on any unexecuted instruction) including 3-deep JMS/BBL
  nesting, 4-JMS stack overflow, ISZ taken/skip, FIN/JIN, all 16 JCN codes,
  DCL bank switching, WRR/RDR loopback, WPM, the page-straddle quirk zones,
  and a fixed-seed random phase (8,192 boundaries).
- Formal verification (`formal/intel_4004.sby`, tasks bmc/prove/cover): a
  golden instruction-set model in `intel_4004_props.sv`, driven by
  `anyconst` instruction words and memory data, is asserted equal to the DUT
  on every architectural register at every clock — proving the complete ISA
  transition function for all encodings and start states — plus
  combinational re-derivation of every output. `intel_4004_cover.sv` proves
  reachability for every instruction group, both branch outcomes, stack
  depth, DCL banks, page-edge fetch, and bus-drive conditions. BMC (ABC
  bmc3), unbounded proof (ABC pdr), and cover (smtbmc z3, --unroll) all
  pass.
- Yosys generic synthesis passes with zero structural problems.
- Fail-fast lint/sim/formal/synth/coverage/aggregate scripts added.
- Chip README, sourced specification, implementation/formal/test plans,
  coverage report, final report, and the sourced `design/README.md` index
  entry added.

## Engineering notes

- SymbiYosys resolves `[files]` paths relative to the invocation directory,
  so `run_formal.sh` runs sby from `formal/` where the `../src` references
  are valid.
- The testbench memory models decode the current opcode by snooping the
  fetch bus (the real chips qualify the command lines at M2/X2 instead);
  this is a documented behavioral-model choice. Like the ISS, they select
  the lowest-numbered active RAM bank when a DCL combination enables
  several lines (the manual restricts base systems to one line; the
  combination rows for expanded banks are OCR-garbled in the surviving
  manual, so the decode is a documented interpretation: line 0 with no bits
  set, lines 1-3 following command-register bits 0-2).
- An initial RTL structure used a default stack write with later
  conditional overrides for the same `stack[sp]` element (ISZ/JCN taken
  path). Yosys and the formal proof resolve the multiple non-blocking
  assignments correctly (last-write-wins), but the project simulator (xezim)
  resolved them first-write-wins, silently keeping the default on taken
  branches. The commit was restructured to compute a single `pc_next`
  combinationally and write each element exactly once — a portable style
  that is also cleaner. Simulation and formal were re-run in full after the
  change.
- Testbench reference-model latches deliberately use the same registered
  bus-capture values as the checker so model updates, reference-model
  fetch, and architectural commit all align to one edge; mixing live and
  captured signals produced one-edge skew that manifested as bank-selection
  mismatches.
- The trace-driven debug loop surfaced one testbench program bug (mis-assem
  -bled FIM opcodes executing as SRC/JUN) that both DUT and reference model
  executed identically — caught by the testbench's executed-instruction
  completeness check rather than by a mismatch.
